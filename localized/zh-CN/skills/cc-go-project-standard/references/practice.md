# Go 工程规范

## 关键检查

1. 定位 go.work 和最近 go.mod，保留模块路径及依赖版本；子模块任务不要直接在根目录 go get。

2. 在明确入口创建依赖，向消费者注入窄接口；创建方负责关闭连接池、客户端和后台任务。

3. 返回可操作错误，用 wrapping 保留原因，按需使用 errors.Is/As；在传输边界映射且不泄露内部细节。

4. 向可阻塞操作传递 context，明确取消归属，不把请求 context 存入全局状态。

5. 在包附近测试行为，覆盖取消、空结果和下游失败；集成与 race 检查限定到变更模块。

6. 格式检查不改文件，运行可用 vet 和测试并记录缺失依赖/工具链；编译成功不能代表已执行测试。

## 边界与案例

适用场景：
- 规划 Go 模块 internal 包边界
- 审查 Go 服务错误和 context 边界
- 避免全局数据库状态增加 repository 适配
- 验证 go.work 中的单个模块

应用角色按实际证据区分；本语言模块可用于库、CLI、桌面或服务，框架问题另选专项。

## 交付要求

- 已读取的工程/契约证据及变更作用域。
- 选用方案、关键不变量、资源/错误或失败边界。
- 实际运行的命令与结果，未运行项及不能证明的结论。
- 兼容、恢复/回滚或后续处理限制；评审结论须给可核实位置。
