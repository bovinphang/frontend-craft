# 以事实来源驱动开发

使用项目事实、权威资料和对应版本的证据做工程决策。

1. 明确问题、版本和本地契约。先读项目清单、配置、实现、调用方和测试；稳定的本地变换可依赖这些事实，运行时、依赖和公共 API 的变化假设需要权威核验。
2. 收集实际版本的官方文档、源码、类型定义、发布记录、规范和迁移指南。第三方讨论只作线索。记录路径或链接、版本、日期和相关结论。
3. 对照运行中的项目说明兼容性、维护成本、迁移范围和回退。通过小的适配边界隔离易变化的外部假设，不为追新直接推翻稳定约定。
4. 使用项目现有校验或最小复现证明关键假设，按实际技术栈选择工具。记录命令和结果；无法验证时明确不确定性，不宣称支持。
5. 公共接口、依赖或团队约定改变时同步轻量 ADR、迁移记录或事实文档，不复制大段外部资料。

## 本地知识请求

用户将来源限制在本地仓库或知识目录时，先检索指定来源，不用网络猜测补齐。使用明确路径，否则检查 `knowledge/` 是否存在；不存在则说明缺失来源，不虚构目录。

有 `data_structure.md` 时先读导航并选择相关分支，渐进搜索而不加载全库。默认最多五轮关键词调整；记录文件、章节/页码/工作表、版本范围与证据缺口。PDF 和表格先选择合适提取工具。只有用户范围允许时才使用外部来源。

## 证据优先级与交付

实现、配置和测试确定本地契约；官方版本化文档与源码确定外部行为；规范确定平台约束；Issue 和文章仅作辅助。交付决策、来源、实现影响、验证结果及剩余不确定性，不能只说“已查文档”。
