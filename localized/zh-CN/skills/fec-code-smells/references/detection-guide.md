# 代码坏味道检测指南

## 证据优先
优先观察代码结构、依赖方向、数据所有权、重复变化模式和实际维护负担。指标只能帮助定位，不能单独证明坏味道。

## 必须执行的误判保护
- 不能仅凭代码行数认定“过长函数”或“过大的类”。
- 单个 `switch` 不能证明“重复的 switch”。
- 函数链或数组管道不自动等于“过长的消息链”。
- 注释本身不是缺陷。
- 不可变的传输数据可以合理地保持纯数据形态。
- React/Vue 声明式组合不自动等于“中间人”。
- `filter().map().reduce()` 管道不是消息链。

## 前端证据检查
- 核对 props、store、API DTO、Hook/Composable 与模块的数据所有权。
- 判断 effect/watch 等生命周期语义后，再评价重复或链式耦合。
- 推荐搬移前核对组件、路由、事件和包导出的公共契约。
- 检查动态引用：懒加载、路由注册、Storybook、i18n key、运行时模板和动态 CSS class。
- 区分真正的领域规则重复与仅仅外观相似的渲染代码。

## 置信度
- **HIGH：** 有直接、重复证据，且重要误判因素已排除。
- **MEDIUM：** 证据成立，但历史、动态引用或所有权仍不完整。
- **LOW：** 主要依据表面指标或存在重大不确定性；只报告，不自动修改。
