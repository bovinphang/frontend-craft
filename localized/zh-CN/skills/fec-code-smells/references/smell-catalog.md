# 代码坏味道目录

本目录基于用户提供资料第 3 章的 24 种坏味道分类，转换为面向前端工程的证据式诊断卡。标准中英文名称与 ID 保持稳定，说明文字为项目化重写。

## SMELL-MYSTERIOUS-NAME — 神秘命名（Mysterious Name）

### 诊断含义
命名无法直接说明程序元素的用途或使用方式。

### 强信号
- 在真实代码中能观察到与上述含义一致的重复依赖、职责混杂、接口不协调或变化耦合。
- 修改该区域时，需要额外追踪多个位置、隐含状态或实现细节才能保持正确。

### 弱信号
- 阅读者经常需要跨文件跳转才能解释当前意图。
- 该区域的结构性修改历史上容易遗漏关联点。

### 误判保护
- 缩写若是团队明确约定且领域内普遍理解，不应仅因缩写而判定坏味道。

### 必须提供的证据
- 指出具体文件/符号，并展示实际的重复关系、变化模式或结构负担；不能只依据行数或复杂度指标下结论。

### 可能影响
- 增加理解成本、变化耦合或结构演进时的回归风险。

### 候选重构

- `RF-RENAME-VARIABLE`
- `RF-RENAME-FIELD`

### 相关坏味道
- 相关坏味道必须独立取证，不因当前坏味道自动成立。

### 前端常见表现
- 可出现在 React/Vue 组件、Hook/Composable、Store、API Client、路由、表单或数据转换代码中；判断时优先检查真实数据所有权、生命周期和公共契约。
